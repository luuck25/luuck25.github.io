1. NULL handling

COALESCE, ISNULL, NULLIF - replace NULLs and dodge divide-by-zero.

COALESCE(a, b, c, ...)   -- first non-NULL (ANSI, 2+ args)
COALESCE(NULL, NULL, 5)   -- 5

ISNULL(expr, replacement)   -- SQL Server only, exactly 2 args
ISNULL(NULL, 0)           -- 0

NULLIF(a, b)               -- NULL if a = b, else a
NULLIF(0, 0)             -- NULL

-- Safe division (the #1 use of NULLIF):
ISNULL(100 / NULLIF(divisor, 0), 0)   -- 0 instead of a divide-by-zero error
ISNULL(a,b)COALESCE(a,b,...)
StandardSQL ServerANSI
Argsexactly 22 or more
Return typetype of 1st arghighest-precedence type
Type pitfall: ISNULL forces the first arg's type. ISNULL(CAST(NULL AS VARCHAR(3)), 'hello world') returns 'hel' (truncated!). COALESCE(...) picks the wider type and returns 'hello world'. Default to COALESCE.

2. Conditional logic

-- Searched CASE (ANSI, any number of conditions):
CASE
    WHEN score >= 90 THEN 'A'
    WHEN score >= 80 THEN 'B'
    ELSE 'F'
END

-- IIF (SQL Server only) - 2 branches, shorthand for CASE:
IIF(amount > 0, 'credit', 'debit')

-- CHOOSE (SQL Server) - 1-based pick from a list:
CHOOSE(2, 'Low', 'Med', 'High')    -- 'Med'

-- Conditional aggregation (pivoting) - the killer pattern:
SUM(CASE WHEN category = 'A' THEN amount ELSE 0 END) AS category_a
CASE evaluates top-to-bottom and stops at the first match - order your WHENs from most specific to least. IIF/CHOOSE are SQL-Server-only sugar; CASE is the portable workhorse.

Use CONCAT, never +, for building strings: the + operator propagates NULL ('a' + NULL = NULL), while CONCAT treats NULL as empty. STRING_AGG(name, ', ') WITHIN GROUP (ORDER BY name) gives you a sorted CSV.

6. Rounding, truncation & number formatting

This is the part everyone gets wrong. Your exact question:

FORMAT(
  ROUND((r.total_returns - p.initial_investment - p.additional_investments)
        * 100.0 / p.initial_investment, 2),
  '0.00'
) AS annual_roi

Why FORMAT if ROUND already rounds to 2 places?

Because ROUND changes the value, FORMAT changes the presentation. They do totally different jobs:

  • ROUND(x, 2) rounds the number mathematically but returns a numeric. It does not guarantee two visible decimals - ROUND(5, 2) is the number 5, which displays as 5, not 5.00. And ROUND(12.5, 2) may display as 12.5.
  • FORMAT(x, '0.00') returns a string with exactly two decimal places, trailing zeros included - 5 becomes '5.00', 12.5 becomes '12.50'. That's the whole point: consistent display for reports/UI.

So the ROUND here isn't even strictly necessary for the display (FORMAT's '0.00' already rounds to 2 places). The pattern is belt-and-suspenders: ROUND fixes the math, FORMAT fixes the look. Note the format is the string '0.00' - writing a bare 0.00 works only because it implicitly converts to text.

Want thousands separators for money? FORMAT(1234567.5, '#,##0.00') -> '1,234,567.50' or the culture shortcut FORMAT(1234567.5, 'N2'). Neither ROUND nor CAST can add commas.

The edge cases (all of them)

Edge caseWhat actually happens
ROUND keeps the type/scaleROUND does NOT drop decimal places - it returns the same type. ROUND(123.456, 2) is 123.460 if the source has scale 3. Use CAST(... AS DECIMAL(p,2)) to actually fix the scale.
ROUND is round-half-up, not banker'sSQL Server rounds halves away from zero: ROUND(2.5,0)=3, ROUND(-2.5,0)=-3. (This differs from .NET/Python banker's rounding.)
ROUND 3rd arg truncatesAny non-zero 3rd arg means "truncate, don't round": ROUND(3.999, 2, 1) = 3.99.
ROUND with negative digitsRounds left of the decimal: ROUND(1234, -2) = 1200.
Integer division truncates FIRSTROUND(5/2, 2) = 2.00 - the 5/2 is integer math (=2) before ROUND runs. Force decimals: 5*1.0/2 or CAST(5 AS DECIMAL(10,2))/2.
FORMAT returns NVARCHARYou can't do math on the result and it sorts alphabetically ('100' < '9'). Only use FORMAT for final display.
FORMAT is slow (CLR)Avoid in WHERE/JOIN/large sets. For fixed-decimal display prefer CAST(x AS DECIMAL(p,2)); use FORMAT only when you need commas/currency/culture.
FORMAT NULL inputFORMAT(NULL, '0.00') returns NULL, not '0.00'. Wrap in COALESCE if needed.
STR() rounds & right-justifiesSTR(num, length, decimals) is an older fixed-width string formatter. It rounds and pads with spaces; returns '****' if the number won't fit the length.
CEILING/FLOOR keep the typeCEILING(3.1) returns 4.0 (same numeric type), not an INT. CAST if you need a true integer.
Practical rule: for a stored/calculated money value use CAST(x AS DECIMAL(19,2)) (correct type, still numeric). For a report/display string with fixed decimals or commas use FORMAT. Use ROUND when you truly need to change the value's precision for further math.

CAST(1 AS DECIMAL(10,2)) / 2   -- 0.50

8. Logical & existence operators

OperatorPurposeExample

NOT IN + NULL = silent empty result. If the subquery in NOT IN (SELECT ...) returns even one NULL, the whole predicate yields no rows. Prefer NOT EXISTS for anti-joins - it's NULL-safe and usually faster on correlated subqueries. Also: BETWEEN is inclusive, which bites on datetimes - use >= start AND < nextDay instead.

9. Set operators & APPLY

OperatorPurposeDuplicates
UNIONCombine, remove dupsDeduped (sorts - slower)

INTERSECTRows in bothDeduped

-- CROSS APPLY = INNER JOIN to a per-row table expression (drops non-matches)
-- OUTER APPLY = LEFT JOIN version (keeps rows, NULLs for no match)
SELECT c.name, o.latest_order
FROM Customers c
CROSS APPLY (
    SELECT TOP 1 order_date AS latest_order
    FROM Orders o WHERE o.customer_id = c.id
    ORDER BY order_date DESC
) o;
Use UNION ALL unless you truly need dedup - UNION adds a sort/distinct step. APPLY shines for "top-N per group" and calling table-valued functions per row (PostgreSQL calls it LATERAL).

10. JSON functions 2016+ some 2022+

Read, test, shape and build JSON right in T-SQL. No native json type - JSON lives in NVARCHAR.

DECLARE @j NVARCHAR(MAX) = '{
  "id": 7,
  "name": "Alice",
  "tags": ["vip", "eu"],
  "address": { "city": "Paris", "zip": "75001" }
}';
FunctionPurposeExample -> result
ISJSON(expr)Valid JSON? (1/0). Type arg in 2022+ISJSON(@j) -> 1
JSON_VALUE(expr,path)Extract a scalar (string/number)JSON_VALUE(@j,'$.name') -> 'Alice'
JSON_QUERY(expr,path)Extract an object or arrayJSON_QUERY(@j,'$.tags') -> '["vip","eu"]'
JSON_MODIFY(expr,path,val)Update/insert/delete a valuesets $.name -> new JSON string
OPENJSON(expr[,path])JSON -> rows (table-valued)shred array/object into a rowset
JSON_PATH_EXISTS(expr,path)Does the path exist? (1/0) 2022+JSON_PATH_EXISTS(@j,'$.zip') -> 0
JSON_OBJECT(...)Build an object 2022+JSON_OBJECT('a':1,'b':2) -> '{"a":1,"b":2}'
JSON_ARRAY(...)Build an array 2022+JSON_ARRAY(1,2,3) -> '[1,2,3]'
FOR JSON PATH / AUTORows -> JSON (query clause)SELECT ... FOR JSON PATH
 
-- Extract scalars vs objects (the key distinction):
JSON_VALUE(@j, '$.address.city')   -- 'Paris'   (scalar - use JSON_VALUE)
JSON_VALUE(@j, '$.tags[0]')        -- 'vip'     (array element by index)
JSON_QUERY(@j, '$.address')        -- '{"city":"Paris","zip":"75001"}' (object)

-- Modify: set, insert (new key), or delete (NULL removes it):
JSON_MODIFY(@j, '$.name', 'Bob')               -- update
JSON_MODIFY(@j, '$.active', CAST(1 AS BIT))  -- insert new key
JSON_MODIFY(@j, '$.tags', NULL)                 -- delete key (in lax mode)

-- Shred an array into rows:
SELECT value FROM OPENJSON(@j, '$.tags');   -- rows: 'vip', 'eu'

-- Shred an object with a typed schema (WITH clause):
SELECT * FROM OPENJSON(@j)
  WITH (
    id   INT            '$.id',
    name NVARCHAR(50)   '$.name',
    city NVARCHAR(50)   '$.address.city',
    tags NVARCHAR(MAX)  '$.tags' AS JSON   -- nested array/object needs AS JSON
  );

-- Build JSON from a result set:
SELECT OrderId, Amount FROM Orders FOR JSON PATH;

Gotchas - JSON

GotchaWhat happens / how to avoid it
JSON_VALUE only returns scalarsPoint it at an object/array and (in lax mode) you get NULL. Use JSON_QUERY for objects/arrays. Reverse is also true: JSON_QUERY on a scalar returns NULL.
lax vs strict path modeDefault is lax - missing paths return NULL silently. Prefix with strict $.x to raise an error when the path is missing.
JSON_VALUE truncates at 4000 charsReturns nvarchar(4000); longer scalars are truncated (lax) or error (strict). Use OPENJSON WITH a wider type for big values.
Nested values in OPENJSON need AS JSONTo pull a nested object/array as a column you must add AS JSON and the column type must be NVARCHAR(MAX).
No index on JSON by defaultFiltering on JSON_VALUE(...) scans. Add a computed column over the JSON_VALUE and index that for SARGable queries.
No native JSON type (pre-2024)JSON is stored as NVARCHAR. Add a CHECK (ISJSON(col) = 1) constraint to guarantee validity. (A dedicated json type arrived in Azure SQL / SQL Server 2025.)
JSON_MODIFY delete needs laxSetting a path to NULL deletes the key in lax mode but sets it to null in strict mode. Know which you want.
