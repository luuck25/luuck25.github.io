What even is a window function?

In layman's terms

Imagine a spreadsheet. A normal GROUP BY squishes many rows into one summary row — you lose the detail. A window function lets you calculate that same summary (a running total, a rank, "yesterday's value") while keeping every original row visible. It looks through a "window" of nearby rows, does the math, and writes the answer next to each row. Nothing gets squished.

In technical terms

A window function performs a calculation across a set of rows (the "window frame") that are related to the current row, defined by the OVER() clause. Unlike aggregates with GROUP BY, it does not collapse rows. Logically it runs after WHERE/GROUP BY/HAVING but before ORDER BY/TOP — which is exactly why you can't use it in a WHERE clause.

Anatomy of the OVER() clause

Every window function is function + OVER(). Three optional knobs live inside OVER:

FUNCTION(...) OVER (
    [ PARTITION BY col1, col2 ]   -- split rows into groups (like GROUP BY, but rows survive)
    [ ORDER BY     col3 ]         -- give the window an order (needed for running/ranking)
    [ ROWS|RANGE BETWEEN ... AND ... ]  -- the frame: which rows count, relative to current row
)

PARTITION BY

Resets the calculation per group. No PARTITION BY = the whole result set is one window.

ORDER BY

Orders rows inside the window. Mandatory for ranking & offset functions.

Frame (ROWS/RANGE)

Narrows the window to a sliding subset. This is where the scary gotchas live.

Aggregate Window Functions

SUM, AVG, COUNT, MIN, MAX — the ordinary aggregates, but with OVER() slapped on so rows survive.

Layman: "Give me the total/average next to each row, not instead of it." Technical: aggregate computed over the window frame instead of a GROUP BY group.

Example — total & running total per region

SELECT SaleId, Region, SaleDate, Amount,
    SUM(Amount)   OVER(PARTITION BY Region)                     AS RegionTotal,
    AVG(Amount)   OVER(PARTITION BY Region)                     AS RegionAvg,
    SUM(Amount)   OVER(PARTITION BY Region ORDER BY SaleDate)    AS RunningTotal
FROM Sales
ORDER BY Region, SaleDate;

What frame do you get by DEFAULT? (RANGE, not ROWS)

When you add ORDER BY to an aggregate window function but don't specify a frame, like: 

SUM(Amount) OVER(PARTITION BY Region ORDER BY SaleDate)

...SQL Server silently applies this default frame:

SUM(Amount) OVER(
    PARTITION BY Region
    ORDER BY SaleDate
    RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW   -- the DEFAULT
)

So the default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW -- not ROWS. Most people assume ROWS and get surprised the moment there's a tie in the ORDER BY column.

ROWS vs RANGE -- identical until there's a tie

ROWS and RANGE return the same result as long as your ORDER BY column has no duplicate values. The moment two rows share an ORDER BY value, they diverge:

ROWS = physical rows

Counts actual rows. A true row-by-row running total: each row includes itself plus everything strictly before it. Ties are treated as separate rows. This is usually what you actually want.

RANGE = logical value peers

All rows sharing the same ORDER BY value are one peer group and are summed together. So tied rows all show the same cumulative total (the sum through the end of that tie group).

Suppose East had two sales on the same date (01-08). Watch the running total split:

The takeaway -- be explicit for real running totals

SUM(Amount) OVER(
    PARTITION BY Region
    ORDER BY SaleDate
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW   -- true row-by-row running total
)

Bonus: ROWS is usually cheaper too -- the default RANGE can force a bigger window spool / worktable in the execution plan.

Gotchas — Aggregate functions

GotchaWhat happens / how to avoid it
ORDER BY secretly changes the frameWithout ORDER BY the default frame is the whole partition (grand total). With ORDER BY it becomes RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW → a running total. Same function, wildly different numbers.
RANGE + ties = surpriseWith the default RANGE frame, tied ORDER BY values are lumped together, so a shared date makes the running total include both rows. Use ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW for a true row-by-row total.
COUNT(*) vs COUNT(col)COUNT(col) ignores NULLs in the window, just like normal aggregation; COUNT(*) counts every row.
No DISTINCT allowedAggregate window functions cannot use DISTINCT — COUNT(DISTINCT x) OVER(...) is illegal in SQL Server.
Can't filter on the alias in WHEREYou can't reference a window column alias in WHERE. Wrap the query in a CTE/subquery and filter in the outer query.

Window Frames: ROWS vs RANGE

Frames belong to the aggregate family (SUM/AVG/COUNT/MIN/MAX and FIRST_VALUE/LAST_VALUE). The frame decides which rows around the current one participate — the #1 source of "why are my numbers wrong?!"

Mental model — the default frame flips based on ORDER BY

ClauseDefault frameResult
OVER() — no ORDER BYRANGE BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWINGGrand total on every row (whole window)
OVER(ORDER BY x) — with ORDER BYRANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROWRunning total (cumulative up to current row)

Adding ORDER BY silently shrinks the upper bound from UNBOUNDED FOLLOWING to CURRENT ROW — turning a grand total into a running total. Handy trick for a % of total: Amount * 100.0 / SUM(Amount) OVER().

ROWS

Counts physical rows around the current row. ROWS BETWEEN 2 PRECEDING AND CURRENT ROW = exactly 3 rows. Predictable, fast, ignores ties. Use this for running totals & moving averages.

RANGE

Works on logical value ranges. All rows with the same ORDER BY value as the current row are treated as one peer group and included together. This is the sneaky default and can inflate running totals on ties.

-- 3-day moving average (current + 2 previous rows)
SELECT Region, SaleDate, Amount,
    AVG(Amount) OVER(
        PARTITION BY Region ORDER BY SaleDate
        ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
    ) AS MovingAvg3
FROM Sales;

-- Common frame keywords:
--   UNBOUNDED PRECEDING  = start of partition
--   N PRECEDING          = N rows before current
--   CURRENT ROW          = the current row
--   N FOLLOWING          = N rows after current
--   UNBOUNDED FOLLOWING  = end of partition

Sum of the 2 rows BEFORE the current row (excluding current)

Want to sum only the two previous rows and leave the current row out? Frame it from 2 PRECEDING to 1 PRECEDING -- the window ends one row before the current one. 

SELECT Region, SaleDate, Amount,
    SUM(Amount) OVER(
        PARTITION BY Region ORDER BY SaleDate
        ROWS BETWEEN 2 PRECEDING AND 1 PRECEDING
    ) AS SumPrev2
FROM Sales;

Gotchas — Frames

GotchaWhat happens / how to avoid it
Default frame is RANGE, not ROWSWith ORDER BY the default is RANGE UNBOUNDED PRECEDING AND CURRENT ROW. On tied values RANGE lumps peers together so a running total can "jump". Write ROWS explicitly for row-by-row behavior.
RANGE with N PRECEDING/FOLLOWINGA numeric range window needs a numeric/date ORDER BY and is only supported in limited forms in SQL Server — most numeric-offset windows require ROWS.
No ORDER BY = whole partitionOVER() with no ORDER BY frames the entire partition (grand total). Ranking functions and PERCENTILE_* can't take a frame at all.
PerformanceROWS is generally cheaper than RANGE, which may build a bigger worktable/spool. Look for a "Window Spool" operator in the plan.
Frames only apply to some functionsA frame only makes sense with aggregates and FIRST_VALUE/LAST_VALUE — remember LAST_VALUE needs ROWS ... UNBOUNDED FOLLOWING.

Ranking Functions

ROW_NUMBER, RANK, DENSE_RANK, NTILE — they number/rank rows. ORDER BY inside OVER() is mandatory.

ROW_NUMBER()

Layman: a strict 1,2,3,4 — no ties ever, even if values are equal (tie broken arbitrarily). Technical: unique sequential integer per partition.

RANK()

Layman: Olympic ranking — ties share a rank, then it skips (1,1,3). Technical: gaps after ties.

DENSE_RANK()

Layman: ties share a rank but no gaps (1,1,2). Technical: consecutive ranks.

NTILE(n)

Layman: chop rows into n roughly-equal buckets (quartiles, deciles). Technical: distributes rows into n groups; earlier groups get the extra rows.

Example — rank salespeople by Amount

SELECT SalesPerson, Amount,
    ROW_NUMBER() OVER(ORDER BY Amount DESC) AS rn,
    RANK()       OVER(ORDER BY Amount DESC) AS rnk,
    DENSE_RANK() OVER(ORDER BY Amount DESC) AS dense,
    NTILE(3)    OVER(ORDER BY Amount DESC) AS tile
FROM Sales;

Gotchas — Ranking functions

GotchaWhat happens / how to avoid it
ROW_NUMBER on ties is non-deterministicIf the ORDER BY column has duplicates, which tied row gets 1 vs 2 can change between runs. Add a tie-breaker (e.g. ORDER BY Amount DESC, SaleId) for stable results — critical for paging & dedup.
RANK leaves gaps, DENSE_RANK doesn'tPick wrong and top-N breaks. "Top 3 distinct amounts" → DENSE_RANK <= 3. "Top 3 rows" → ROW_NUMBER <= 3.
NTILE is NOT percentile-basedIt counts rows into equal buckets and ignores the actual values. Two identical amounts can land in different tiles — don't use it for value-based cutoffs.
NTILE uneven splitWhen rows don't divide evenly, the first groups get the extra rows (3,2,2 — not 2,2,3).
ORDER BY required, no frameThese functions require ORDER BY in OVER() and cannot take a ROWS/RANGE frame clause.
Classic dedup patternROW_NUMBER() OVER(PARTITION BY dupKey ORDER BY ...) = 1 keeps one row per duplicate group.

Offset & Value Functions

LAG, LEAD, FIRST_VALUE, LAST_VALUE — peek at other rows relative to the current one.

LAG(col, n, default)

Layman: "what was the value n rows ago?" (previous). Technical: accesses a prior row without a self-join.

LEAD(col, n, default)

Layman: "what's the value n rows ahead?" (next). Perfect for "days until next purchase".

FIRST_VALUE(col)

Layman: the first value in the window. E.g. the earliest sale amount per region.

LAST_VALUE(col)

Layman: the last value in the window — but the default frame will lie to you (see gotcha ).

Example — compare each sale to the previous/next one

SELECT Region, SaleDate, Amount,
    LAG(Amount, 1, 0)  OVER(PARTITION BY Region ORDER BY SaleDate) AS PrevAmount,
    LEAD(Amount, 1, 0) OVER(PARTITION BY Region ORDER BY SaleDate) AS NextAmount,
    Amount - LAG(Amount, 1, 0) OVER(PARTITION BY Region ORDER BY SaleDate) AS DiffFromPrev,
    FIRST_VALUE(Amount) OVER(PARTITION BY Region ORDER BY SaleDate) AS FirstInRegion,
    -- LAST_VALUE needs an explicit full frame to behave!
    LAST_VALUE(Amount) OVER(PARTITION BY Region ORDER BY SaleDate
        ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS LastInRegion
FROM Sales
ORDER BY Region, SaleDate;

Gotchas — Offset & Value functions

GotchaWhat happens / how to avoid it
THE big one: LAST_VALUE returns the current rowDefault frame with ORDER BY is RANGE UNBOUNDED PRECEDING AND CURRENT ROW, so "last" is always the current row. Add ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING for the true final value. (FIRST_VALUE is safe.)
LAG/LEAD default is NULL at edgesThe first row's LAG and last row's LEAD have nothing to point at. Supply the 3rd argument (default) to avoid NULLs.
Offset must be non-negativeThe 2nd arg is a non-negative constant/expression — you can't LAG a negative number (use LEAD instead), and it can't reference a per-row column value in older versions.
LAG/LEAD ignore the frame clauseThey only care about ORDER BY + offset. Don't try to add ROWS/RANGE to them.
NULLs are returned as-isLAG doesn't skip NULLs to find the last non-null (no IGNORE NULLS before SQL Server 2022; 2022+ adds it for these functions).
Ties make FIRST/LAST_VALUE ambiguousAdd a tie-breaker column to ORDER BY for deterministic results.

Statistical / Distribution Functions

PERCENT_RANK, CUME_DIST, PERCENTILE_CONT, PERCENTILE_DISC — relative standing & percentiles.

PERCENT_RANK()

Layman: "what % of rows rank below me?" Ranges 0→1. Formula: (rank-1)/(rows-1). First row always 0.

CUME_DIST()

Layman: cumulative distribution — "% of rows at or below my value". Ranges (0→1]. Last row always 1.

PERCENTILE_CONT(p)

Layman: the value at percentile p, interpolated (can return a value not in the data — e.g. a median between two numbers).

PERCENTILE_DISC(p)

Layman: the value at percentile p, discrete — always returns an actual value from the data set.

Example — distribution & median of Amount

SELECT SalesPerson, Amount,
    PERCENT_RANK() OVER(ORDER BY Amount) AS pct_rank,
    CUME_DIST()    OVER(ORDER BY Amount) AS cume_dist,
    -- NOTE the weird WITHIN GROUP syntax + OVER(PARTITION BY)
    PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY Amount) OVER() AS median_cont,
    PERCENTILE_DISC(0.5) WITHIN GROUP (ORDER BY Amount) OVER() AS median_disc
FROM Sales;

Gotchas — Statistical functions

GotchaWhat happens / how to avoid it
Bizarre syntaxPERCENTILE_CONT/DISC use WITHIN GROUP (ORDER BY ...) OVER (PARTITION BY ...) — the ORDER BY lives in WITHIN GROUP, and OVER() takes only PARTITION BY (no ORDER BY, no frame).
CONT interpolates, DISC doesn'tWith an even row count PERCENTILE_CONT(0.5) can return a value not in your data (average of the two middle rows). PERCENTILE_DISC(0.5) always returns a real existing value.
Same value on every rowPERCENTILE_* return a partition-wide scalar repeated on every row. Wrap in DISTINCT/aggregate if you only want one row.
PERCENT_RANK vs CUME_DIST edgesPERCENT_RANK first row is always 0; CUME_DIST last row is always 1. PERCENT_RANK uses (rank-1)/(n-1), CUME_DIST uses (rows ≤ current)/n.
Can be expensivePERCENTILE functions sort the whole partition — watch the execution plan on large sets.
NULL handling differsNULLs are ignored by PERCENTILE_* but affect the counts in PERCENT_RANK/CUME_DIST depending on placement.

Master Gotchas (the ones that page you at 2am)

#GotchaWhat happens / how to avoid it
1Can't use in WHERE / GROUP BY / HAVINGWindow functions run after those clauses. Wrap the query in a CTE/subquery and filter on the alias in the outer query.
2OVER() ORDER BY ≠ query ORDER BYThe OVER() ORDER BY only orders the window computation. Final row order is undefined unless you add a query-level ORDER BY.
3ORDER BY turns aggregate into running totalSUM(x) OVER(PARTITION BY r) = grand total. Add ORDER BY d and it becomes a running total. One tiny change, very different results.
4LAST_VALUE lies without a frameAlways add ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING to get the real last value.
5Non-deterministic tiesROW_NUMBER, FIRST_VALUE, LAG etc. give unstable results when ORDER BY has duplicates. Add a unique tie-breaker for reproducibility (paging, dedup, ETL).
6No DISTINCT in a window aggregateCOUNT(DISTINCT x) OVER(...) is not supported. Use a subquery/derived table or the DENSE_RANK trick.
7Reuse windows with WINDOW clause (2022+)Repeating the same long OVER(...)? SQL Server 2022 supports the named WINDOW clause. On older versions you copy-paste (DRY weeps).
8Integer division in AVG / running mathIf the column is INT, AVG and arithmetic truncate. Cast to DECIMAL/FLOAT first.
9Give it the right indexAn index matching PARTITION BY then ORDER BY lets SQL Server skip a sort. Watch for expensive Sort + Window Spool operators; batch mode (columnstore / 2019+) speeds windows up a lot.
