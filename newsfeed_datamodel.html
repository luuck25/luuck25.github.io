1. The star schema

A newsfeed platform delivers personalised content and processes millions of interactions daily (views, likes, shares, comments). Following Kimball's 4 steps (Process → Grain → Dimensions → Facts), it becomes one fact surrounded by five dimensions.

  • Business process: user engagement with content.
  • Grain (one fact row): a single user interaction with a post — one view, like, share, or comment.
  • Fact: user_action_fact — 6 foreign keys + 2 measures.
  • Dimensions: date_dim, user_dim, post_dim, interaction_type_dim, device_dim.

LAYMAN

The fact is the "activity log" (skinny & tall — who did what to which post, when, on what device). The dimensions are the "address books" that turn the log's ID numbers into readable descriptions. One row of the fact = one tap/scroll event.

4. Design Q&A

What does duration tell you?

It's a measure (a numeric fact), not a key: the view/dwell time in seconds. A 1-second view is a scroll-past; a 45-second view means they actually read/watched. For like/share/comment there's no span, so it's NULL — and that's allowed (non-FK columns in a fact may be null; foreign keys must never be null).

SMELL

Cramming a "view duration" into a generic action fact where 3 of 4 interaction types can't use it means most rows carry a NULL measure. A purist might split views into their own fact. The article keeps them together for simplicity — a fair trade-off, just know why the NULLs exist.

Do we really need a separate interaction_type_dim?

Judgment call — the classic "is this a degenerate dimension?" question.

Keep the dimension because…Or inline it (degenerate) because…
"No free text in facts" — store the label once, not on every billion rows (saves space, prevents typos).It has just ONE attribute and ~4 rows — a whole table for one column feels heavy.
Cheap to extend: add reaction_type, engagement_category, weight, icon — without touching the fact.Fewer joins for such a tiny list.
Uniformity: every other descriptor is a dimension.YAGNI — don't build for growth that may never come.

RULE OF THUMB

One attribute + never going to grow → degenerate dimension (inline it). One attribute today but likely to gain descriptors (reactions, weights, categories) → keep the small dimension. Interaction type almost always grows, so keeping it is the low-regret choice.

5. Deriving a metric (the thought process)

THE ONE MENTAL MODEL

Every metric = a NUMBER, at a GRAIN, over a FILTER.

  • NUMBER = what you measure + how you aggregate → SELECT aggregates
  • GRAIN = "per what" it breaks down → GROUP BY
  • FILTER = which subset → WHERE

The 6-step recipe

  1. Restate precisely: "<aggregation> of <thing>, per <grain>, for <filter>."
  2. Nail the unit of the number: counting events (COUNT(*)) or entities (COUNT(DISTINCT key)) or summing an amount (SUM)?
  3. If it's a rate/average, split numerator ÷ denominator explicitly.
  4. Map to the star: measured quantity → fact; every "per/by/each" → a dimension (JOIN + GROUP BY); every "for <condition>" → WHERE.
  5. Assemble in logical order (FROM → WHERE → GROUP BY → SELECT aggregates → ORDER BY).
  6. Sanity-check: smell test, edge cases (NULLs, /0, ties), grain check, traps (100.0, distinct).

English → SQL dictionary

English signalSQL
"how many"COUNT(*)
"how many unique/distinct"COUNT(DISTINCT …)
"total / sum of"SUM(measure)
"average"AVG(…) or explicit SUM/COUNT
"per X" / "by X" / "for each X"GROUP BY X (+ JOIN its dim)
"% / share / rate / proportion"ratio, usually … / SUM(…) OVER()
"top / most / biggest"ORDER BY … DESC (+ LIMIT)
"over time / daily / trend"GROUP BY date
"compare A vs B"GROUP BY <that dimension>
"at least / more than N" (on a group)HAVING
"within each X" (nested %)OVER (PARTITION BY X)

6. Numerator vs Denominator — the hack

THE HACK

The word after "of" or "per" is the DENOMINATOR (the base / the whole / "out of what"). The NUMERATOR is the special subset.

Questionafter "of/per" → denominatornumerator
% of viewers who engageviewersengaged viewers
% of posts that go viralall postsviral posts
interactions per userusersinteractions
avg duration per viewviewstotal duration
conversion rate (buyers of visitors)visitorsbuyers

TWO SANITY CHECKS

  • Subset test: numerator ⊆ denominator, so the % must be ≤ 100%. If it exceeds 100%, you flipped them (or have a data gap).
  • Read aloud with units: it should sound natural as "<numerator> per <denominator>" (e.g. "2 interactions per 1 user" — correct; "1 user per 2 interactions" — flipped).

NO "of/per" IN THE SENTENCE?

Ask: "this is a fraction OUT OF what total?" That total is the denominator. For percentages, the denominator is the number the parts add up to 100% against.

7. Averages = SUM ÷ COUNT

CORE RULE

An average is always SUM(top) ÷ COUNT(bottom). Numerator = SUM of the values; denominator = COUNT of the items. And the word after "per" is still the denominator.

"average ___ per ___"NumeratorDenominator
avg duration per viewSUM(duration)COUNT(views)
avg interactions per userCOUNT(interactions)COUNT(DISTINCT user)
avg order value per orderSUM(amount)COUNT(orders)

Two flavours:

  • Built-in AVG(x) = SUM(x)/COUNT(x) where COUNT(x) counts non-NULL values only.
  • Manual SUM / COUNT(DISTINCT…) when the denominator is an entity (per user/post), not table rows.

TWO TRAPS (both "wrong denominator")

  • NULLs shrink the denominator. AVG(duration) on [8, NULL, 3, NULL, NULL] = 11/2 = 5.5 (divides by 2 non-nulls, not 5). Want NULL treated as 0? Use AVG(COALESCE(duration,0)) or SUM(duration)/COUNT(*).
  • "Per entity" needs COUNT(DISTINCT). Avg interactions per user = COUNT(*) / COUNT(DISTINCT user) = 5/3 = 1.67, NOT plain AVG over rows.

8. Choosing the grain (overall vs per-post vs …)

Grain is a choice, not a property of the metric — same definition, just a different GROUP BY. Read the grain from the question's words:

If the question contains…Grain
"per X", "by X", "for each X", "across X"per X (GROUP BY X)
"which posts / users / devices…"per that entity (+ ranking)
"over time / daily / trend"per date
none of the above — just "what % / how many / what's the rate"overall (one number)

HOW TO BE SURE

  1. Signal words (table above) — absence of "per/by/each/which" → overall.
  2. Shape of the answer: one big KPI number → overall; a table/ranking → per-entity.
  3. The "so what" / decision: health KPI → overall; optimise specific items → breakdown.
  4. Still unsure? Confirm the grain before coding. Never infer it silently — wrong grain = perfect query, wrong answer.

BIG TRAP — non-additivity across grains

You cannot average per-post percentages to get the overall percentage, and you can't sum COUNT(DISTINCT user) across groups. Distinct-counts and ratios are non-additive across grains — to change grain you recompute from the fact rows, never roll up the finer results. (Example: per-post gave 50% & NULL; true overall was a totally different number.)

PRO PATTERN

Deliver the headline (overall) that answers the literal question, then offer the drill-down (per post/device/segment) as the anticipated follow-up.

9. How SQL actually runs (logical phases)

You write SELECT…FROM…GROUP BY…ORDER BY, but the engine evaluates in a fixed order. This explains how you can compute on a grouped result "on the fly."

PhaseClauseProduces
1FROM / JOINcombined rows (fact ⋈ dim)
2WHEREfiltered raw rows
3GROUP BY + aggregatesone row per group, COUNT/SUM computed
4HAVINGfiltered groups
5SELECT (incl. window functions)window funcs run HERE, on the grouped rows
6ORDER BYsorted output

WHAT "ON THE FLY" MEANS

Window functions live in phase 5, after GROUP BY collapsed millions of rows into a handful of grouped rows in phase 3. So yes — SQL genuinely computes a second layer of math on the already-grouped result. The big fact table is scanned once; the window pass then works on the tiny grouped set already in memory (no re-scan).

10. Window functions & OVER()

Query A: "What are the most common user interactions?"

What we're computing: a ranked leaderboard of interaction types (view / like / comment / share) with each one's raw count and its share (%) of all interactions — so you can see, e.g., "views are 40% of activity, likes 20%…"

SELECT it.interaction_name,
       COUNT(*) AS interaction_count,
       COUNT(*) * 100.0 / SUM(COUNT(*)) OVER() AS percentage
FROM   user_action_fact uaf
JOIN   interaction_type_dim it ON uaf.interaction_type_dim_sk = it.interaction_type_dim_sk
GROUP BY it.interaction_name
ORDER BY interaction_count DESC;

SUM(COUNT(*)) OVER() is a double aggregation: the inner COUNT(*) is the group aggregate (phase 3, gives [2,1,1,1]); the outer SUM(…) OVER() is a window aggregate over those grouped rows (phase 5) — it sums them to the grand total (5) and stamps that total onto every row without collapsing them.

RESULT on sample data (total interactions = 5)

Query B: "When do users most actively engage with content?"

What we're computing: activity by hour of day over the last 30 days — both total interactions and unique users per hour — to find peak engagement times (e.g. lunchtime, late-evening scrolling).

SELECT EXTRACT(HOUR FROM uaf.interaction_timestamp) AS hour_of_day,
       COUNT(*) AS interaction_count,
       COUNT(DISTINCT uaf.user_dim_sk) AS unique_users
FROM   user_action_fact uaf
JOIN   date_dim d ON uaf.date_dim_sk = d.date_dim_sk
WHERE  d.date >= CURRENT_DATE - INTERVAL '30 days'
GROUP BY EXTRACT(HOUR FROM uaf.interaction_timestamp)
ORDER BY interaction_count DESC;

How it works: EXTRACT(HOUR FROM …) pulls just the 0–23 hour off the timestamp, and that becomes the grain (GROUP BY it). Note two different counts: COUNT(*) = total events; COUNT(DISTINCT user_dim_sk) = distinct people active that hour (so one power-user spamming at 2am doesn't fake a "peak"). The WHERE d.date >= CURRENT_DATE - INTERVAL '30 days' is the FILTER — last 30 days only. Grain = per hour-of-day.

Query C: "Which posts generate the most engagement?"

What we're computing: per post, a breakdown of views / likes / comments / shares in separate columns, keeping only posts above a minimum activity threshold — a content leaderboard.

SELECT p.post_id, p.post_type, p.category,
       COUNT(DISTINCT CASE WHEN it.interaction_name = 'view'    THEN uaf.user_action_fact_sk END) AS views,
       COUNT(DISTINCT CASE WHEN it.interaction_name = 'like'    THEN uaf.user_action_fact_sk END) AS likes,
       COUNT(DISTINCT CASE WHEN it.interaction_name = 'comment' THEN uaf.user_action_fact_sk END) AS comments,
       COUNT(DISTINCT CASE WHEN it.interaction_name = 'share'   THEN uaf.user_action_fact_sk END) AS shares
FROM   post_dim p
JOIN   user_action_fact uaf ON p.post_dim_sk = uaf.post_dim_sk
JOIN   interaction_type_dim it ON uaf.interaction_type_dim_sk = it.interaction_type_dim_sk
GROUP BY p.post_id, p.post_type, p.category
HAVING COUNT(*) > 100   -- minimum engagement threshold
ORDER BY views DESC;

How it works: this is conditional aggregation (the same trick from the "% of viewers" example) — each COUNT(DISTINCT CASE WHEN … END) counts only the rows matching that interaction type, giving one column per metric in a single pass. The HAVING COUNT(*) > 100 filters after grouping (it's a filter on the aggregate, which WHERE can't do) to drop low-signal posts. Grain = per post.

WHERE vs HAVING

WHERE filters raw rows before grouping (e.g. last 30 days). HAVING filters groups after aggregation (e.g. only posts with >100 interactions). You can't put an aggregate like COUNT(*) > 100 in WHERE — the count doesn't exist yet at that phase (remember the phase order: WHERE=2, GROUP BY=3, HAVING=4).

Back to the window function — blank OVER()

Empty OVER() has three missing pieces, each with a default:

MissingDefault
PARTITION BYno partitioning → the WHOLE result is one group (all rows)
ORDER BYno ordering
framethe ENTIRE partition

So blank OVER() = "every row as one group" = equivalent to:

SUM(COUNT(*)) OVER (ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING)

It's unbounded both directions (all rows), not a fixed "n preceding/following." A sliding window would be ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING (that's for moving averages).

THE FRAME GOTCHA — adding ORDER BY changes everything

The default frame flips depending on ORDER BY:

row (cnt)SUM OVER () — blankSUM OVER (ORDER BY cnt DESC)
view (2)52
like (1)53
comment (1)54
share (1)55

Blank = grand total everywhere. Add ORDER BY and the frame silently becomes "UNBOUNDED PRECEDING … CURRENT ROW" → you get a running total instead. The percentage query needs the constant total, so it keeps OVER() blank.

What if you remove OVER()?

SUM(COUNT(*)) without OVER() is a nested aggregate at the same level:

  • Postgres / SQL Server / MySQL / BigQuery / Snowflake → hard error ("aggregate function calls cannot be nested").
  • Oracle → permits it but collapses to a single grand-total row, which then clashes with the per-group columns (ORA-00937: not a single-group group function).

OVER() is what legalises the double aggregation while keeping your per-group rows. Without a window you'd need a subquery: … / (SELECT COUNT(*) FROM user_action_fact) * 100.0 — but that scans the table twice.

When the window is NOT blank — PARTITION BY

Add PARTITION BY X to compute "% within each X" (e.g. share of interactions within each device, or within each day). The total then resets per partition, so percentages sum to 100% within each group.

11. The magic of 100.0

In SQL, the type of a division depends on its operands: integer ÷ integer = integer (the fraction is truncated, not rounded). COUNT(*) and SUM(…) return integers, so a naive percentage silently breaks.

THE BUG

COUNT(*) / SUM(...) OVER() with views=2, total=5 → 2/5 floors to 0. Every percentage becomes 0. Ouch.

The fix — type promotion. The literal 100.0 is a decimal, so it "infects" the expression with decimal type before the division:

-- runs left to right: ( COUNT(*) * 100.0 ) / total
COUNT(*) * 100.0 / SUM(COUNT(*)) OVER()
-- 2 * 100.0 = 200.0 (decimal) ; 200.0 / 5 = 40.0  correct!

ORDER MATTERS — the trap within the trap

expressionviews (2/5)
COUNT(*) * 100.0 / total (good: multiply first)200.0/5 = 40.0
COUNT(*) / total * 100.0 (bad: divide first)0 * 100.0 = 0.0

Multiply by 100.0 before the division, or the integer division already destroyed the fraction.

Equivalents: CAST(x AS DECIMAL), x::numeric (Postgres), or * 1.0. Tidy output: wrap in ROUND(…, 2).

ONE-LINER

100.0 (not 100) sneaks a decimal into the math before the division, dodging integer-division truncation — and it must come before the /. MySQL/SQLite are lenient; Postgres/SQL Server/Oracle are not — so always write 100.0.

12. NULLIF, divide-by-zero & NULL handling

Guarding division with NULLIF

NULLIF(a, b) returns NULL if a = b, else a. So NULLIF(denom, 0) turns a zero denominator into NULL, and the division yields NULL instead of a divide-by-zero crash.

-- viewers = 0, engagers = 2
engagers * 100.0 / NULLIF(viewers, 0)
= 2 * 100.0 / NULLIF(0,0)   -- NULLIF(0,0) = NULL
= 200.0 / NULL              -- any math with NULL = NULL
= NULL                       (not a crash, not 0)

WHY NULL IS THE RIGHT ANSWER

"% of viewers" is genuinely undefined when there are zero viewers (it's 0/0). NULL honestly says "can't compute / not applicable" — better than a fake 0% ("measured, no engagement") or a misleading 100%. NULL = undefined; 0 = measured and it's zero. Don't blur them.

Want to display something instead of NULL? Wrap with COALESCE: COALESCE(…, 0) shows 0, COALESCE(…, 'N/A') shows text — but choose deliberately.

How aggregates treat NULLs (each differently!)

FunctionNULL behaviour
COUNT(*)counts ALL rows, including those with NULLs
COUNT(col)counts only NON-NULL values of col
SUM(col) / AVG(col)ignore NULLs (AVG divides by non-null count)
COUNT(DISTINCT col)ignores NULLs; counts distinct non-null values

CLASSIC MISREAD

AVG(duration) over [8, NULL, 3, NULL, NULL] = 5.5 (11 ÷ 2 non-nulls), NOT 2.2. If you expected NULL to mean 0, you got the wrong denominator. Use AVG(COALESCE(duration,0)) or SUM(duration)/COUNT(*).

13. Worked example — "% of viewers who engage beyond just viewing?"

Step 1 — precise definition (engaged viewers ÷ ALL viewers):

  • Denominator = distinct users who viewed (the whole viewer pool — NOT just the passive ones).
  • Numerator = distinct viewers who also did a non-view interaction (like/share/comment).

DENOMINATOR TRAP

"% of viewers" → denominator = ALL viewers (engaged + passive), giving engaged/100. It is NOT engaged ÷ passive-only (that's an odds ratio, a different metric). 100 viewers, 30 engaged → 30%, not 30/70 = 43%.

Step 4 — the key technique: conditional aggregation (COUNT(DISTINCT CASE WHEN … END)) gives numerator and denominator from the same rows in one pass. CASE returns the key when matched else NULL, and COUNT(DISTINCT) ignores NULLs.

Per-post version:

SELECT p.post_id,
  COUNT(DISTINCT CASE WHEN it.interaction_name = 'view'  THEN uaf.user_dim_sk END) AS viewers,
  COUNT(DISTINCT CASE WHEN it.interaction_name <> 'view' THEN uaf.user_dim_sk END) AS engagers,
  COUNT(DISTINCT CASE WHEN it.interaction_name <> 'view' THEN uaf.user_dim_sk END) * 100.0
     / NULLIF(COUNT(DISTINCT CASE WHEN it.interaction_name = 'view' THEN uaf.user_dim_sk END), 0) AS pct_engaged
FROM user_action_fact uaf
JOIN interaction_type_dim it ON uaf.interaction_type_dim_sk = it.interaction_type_dim_sk
JOIN post_dim p ON uaf.post_dim_sk = p.post_dim_sk
GROUP BY p.post_id
ORDER BY pct_engaged DESC;

RESULT (per post)

post_idviewersengagerspct_engaged
P50012150.0
P500202NULL

P5001 = clean 50%. P5002 = 0 viewers but 2 engagers → NULLIF prevented a /0 crash → NULL. P5003 has no interactions so it doesn't appear (a GROUP BY only sees existing rows; LEFT JOIN from post_dim to show it as 0).

Overall version (the literal answer — drop GROUP BY & post_dim):

SELECT
  COUNT(DISTINCT CASE WHEN it.interaction_name = 'view'  THEN uaf.user_dim_sk END) AS viewers,
  COUNT(DISTINCT CASE WHEN it.interaction_name <> 'view' THEN uaf.user_dim_sk END) AS engagers,
  COUNT(DISTINCT CASE WHEN it.interaction_name <> 'view' THEN uaf.user_dim_sk END) * 100.0
     / NULLIF(COUNT(DISTINCT CASE WHEN it.interaction_name = 'view' THEN uaf.user_dim_sk END), 0) AS pct_engaged
FROM user_action_fact uaf
JOIN interaction_type_dim it ON uaf.interaction_type_dim_sk = it.interaction_type_dim_sk;

On sample data: viewers = {502,503} = 2, engagers = {501,502,503} = 3 → 150% (user 501 shared but never viewed — the data gap again). Strict "viewed AND engaged" = 100%. This is why overall ≠ average of per-post (per-post gave 50% & NULL).

14. Engagement vs Share (mobile vs desktop)

"Are users more engaged on mobile vs desktop?" is not answered by device share of interactions. They measure different things:

MetricTells youQuestion it answers
% share of interactionsvolume distribution"Where does most activity come from?" (reach)
avg interactions per user + avg durationper-person intensity"Are users more engaged on X?" (engagement)

WHERE THEY DISAGREE

Mobile: 1,000 users × 2 = 2,000 interactions. Desktop: 100 users × 20 = 2,000 interactions. By share they tie (50/50). By per-user engagement desktop is 10× more engaged (20 vs 2). Share is confounded by how many users are on each device — so for "engagement," always normalise per user (divide by COUNT(DISTINCT user)).

REMEMBER

Share = volume/reach ("where activity happens"). Per-user averages = engagement ("how hard each person leans in"). For "more engaged," normalise per user — share alone can point the opposite way.

15. The data-gap insight (separate events)

The fact grain is one row per interaction, per type — a view is its own row, a like is a separate row. Liking a post does not auto-create a view row. So a post can show engagement with zero view rows.

WHAT "0 VIEWERS" REALLY MEANS

It does not mean "everyone engaged." In reality you cannot like/share/comment a post you never saw — engagement implies a view. So "engagement but no view rows" = the view events weren't logged (a data gap), not that there were no viewers.

The robust fix: since engaging proves a view happened, define viewers = distinct users with ANY interaction (view OR engage), not just the 'view' rows:

COUNT(DISTINCT uaf.user_dim_sk) AS viewers  -- ANY interaction => they saw it

RESULT with the robust denominator

postviewers (any interaction)engagerspct_engaged
P50012150%
P500222100%

No more NULL, no more >100%. This definition is immune to missing view rows.

TAKEAWAY

Because interactions are stored as separate events, a missing view row means missing data, not "no viewers." Since engaging implies viewing, "viewers = anyone who interacted" makes the metric robust. Bigger lesson: always ask whether the data faithfully represents reality — that's modelling, not just querying.
