2. Extracting date parts

DATEPART, DATENAME, and the DAY/MONTH/YEAR shortcuts.

DATEPART(part, date)

Returns an int. Use for math and comparisons. E.g. DATEPART(MONTH, d) = 4.

DATENAME(part, date)

Returns a varchar. Use only for text names. E.g. DATENAME(MONTH, d) = 'April'.

When do they actually differ? Only MONTH and WEEKDAY:

PartDATEPART()DATENAME()Different?
MONTH4'April'Yes - name vs number
WEEKDAY5'Thursday'Yes - name vs number
YEAR2026'2026'No (just type)
DAY23'23'No (just type)
 
-- Use DATEPART for math/comparison:
WHERE DATEPART(MONTH, OrderDate) = 4

-- Use DATENAME only for display text:
SELECT DATENAME(MONTH,   OrderDate);   -- 'April'
SELECT DATENAME(WEEKDAY, OrderDate);   -- 'Thursday'

-- Shortcuts: DAY / MONTH / YEAR == DATEPART(...)
SELECT YEAR(OrderDate), MONTH(OrderDate), DAY(OrderDate);
-- No shortcut for HOUR/MINUTE/WEEK - use DATEPART for those.

-- Pivot by day name:
SUM(CASE WHEN DATENAME(WEEKDAY, OrderDate) = 'Monday' THEN Amount ELSE 0 END) AS Monday
Rule of thumb: default to DATEPART everywhere; reach for DATENAME only when you need the word ('April'/'Thursday'). The DAY()/MONTH()/YEAR() shortcuts are just less typing for the same result.

3. Date arithmetic

DATEADD adds/subtracts intervals; DATEDIFF measures the gap; DATEDIFF_BIG handles huge gaps.

-- DATEADD(part, number, date): add or subtract
DATEADD(DAY,    7, '2026-04-23')          -- 2026-04-30
DATEADD(DAY,   -1, '2026-04-23')          -- 2026-04-22 (yesterday)
DATEADD(MONTH,  1, '2026-01-31')          -- 2026-02-28 (clamps!)
DATEADD(HOUR,   3, '2026-04-23 10:00')     -- 2026-04-23 13:00

-- DATEDIFF(part, start, end) = end - start
DATEDIFF(DAY,   '2026-04-01', '2026-04-23')   -- 22
DATEDIFF(MONTH, '2026-01-01', '2026-04-23')   -- 3
DATEDIFF(MINUTE,'10:00',      '10:45')        -- 45

-- DATEDIFF_BIG: use when the answer overflows INT (e.g. seconds over ~68 yrs)
DATEDIFF_BIG(SECOND, '1970-01-01', SYSUTCDATETIME())
DATEDIFF counts boundary crossings, not full intervals. DATEDIFF(YEAR, '2025-12-31', '2026-01-01') = 1 (crossed a year boundary) even though the dates are 1 day apart. Same trap with MONTH: DATEDIFF(MONTH, '2026-01-31', '2026-02-01') = 1.

Handy patterns:

-- "Day after install" (retention):
WHERE DATEDIFF(DAY, install_dt, event_date) = 1
-- or equivalently:
WHERE event_date = DATEADD(DAY, 1, install_dt)

-- Age in whole years (correct - no boundary bug):
DATEDIFF(YEAR, dob, GETDATE())
  - CASE WHEN DATEADD(YEAR, DATEDIFF(YEAR, dob, GETDATE()), dob) > GETDATE()
         THEN 1 ELSE 0 END

-- Gaps-and-islands: consecutive dates share a constant group key
DATEADD(DAY, -ROW_NUMBER() OVER(ORDER BY d), d) AS grp

4. Truncation & bucketing

DATETRUNC (fixed 1-unit), DATE_BUCKET (custom N-unit), and EOMONTH.

-- DATETRUNC(part, date): zero out everything below 'part'  (2022+)
-- Given '2026-04-23 14:35:47.123':
DATETRUNC(YEAR,   d)   -- 2026-01-01 00:00:00
DATETRUNC(MONTH,  d)   -- 2026-04-01 00:00:00
DATETRUNC(DAY,    d)   -- 2026-04-23 00:00:00 (strip time)
DATETRUNC(HOUR,   d)   -- 2026-04-23 14:00:00

-- Pre-2022 workaround for month truncation (0 = 1900-01-01 epoch):
DATEADD(MONTH, DATEDIFF(MONTH, 0, OrderDate), 0)   -- first of month

Custom-size buckets with DATE_BUCKET 2022+:

-- DATE_BUCKET(part, width, date [, origin])
DATE_BUCKET(MINUTE, 15, event_time)   -- 15-minute buckets: 10:00, 10:15, 10:30...
DATE_BUCKET(HOUR,    3, event_time)   -- 3-hour buckets: 09:00, 12:00, 15:00
DATE_BUCKET(DAY,     7, event_time)   -- weekly buckets
DATE_BUCKET(MONTH,   3, event_time)   -- quarterly buckets

-- Group daily/monthly (most common real-world use):
SELECT DATETRUNC(MONTH, OrderDate) AS mth, SUM(Amount)
FROM Orders
GROUP BY DATETRUNC(MONTH, OrderDate);
-- EOMONTH: last day of the month (handles 28/29/30/31 for you)
EOMONTH('2026-04-22')       -- 2026-04-30
EOMONTH('2026-02-10')       -- 2026-02-28 (leap-aware)
EOMONTH('2026-04-22', 1)    -- 2026-05-31 (+1 month)

-- First day of month = day after previous month's end:
DATEADD(DAY, 1, EOMONTH(OrderDate, -1))

DATETRUNC vs DATE_BUCKET: DATETRUNC always makes 1-unit buckets (one month, one hour). DATE_BUCKET lets you pick the width (15 min, 3 months). Both are 2022+.

6. Converting & formatting

CAST (ANSI), CONVERT (style codes), FORMAT (.NET patterns), and the safe TRY_* / PARSE variants.

CAST

ANSI, portable, no formatting. Default choice.

CONVERT

SQL Server only. Fast. Has style codes for dates. Use when you need a specific style.

FORMAT

.NET patterns. Most flexible but slow (CLR). Display only. 2012+

-- CAST vs CONVERT (identical when no style needed):
CAST(GETDATE() AS DATE)          -- 2026-04-23
CONVERT(DATE, GETDATE())         -- 2026-04-23

-- CONVERT style codes (the main reason to use CONVERT):
CONVERT(VARCHAR, GETDATE(), 101)  -- 04/23/2026  (US)
CONVERT(VARCHAR, GETDATE(), 103)  -- 23/04/2026  (UK)
CONVERT(VARCHAR, GETDATE(), 112)  -- 20260423    (ISO compact)
CONVERT(VARCHAR, GETDATE(), 120)  -- 2026-04-23 14:30:45 (ODBC)
CONVERT(VARCHAR, GETDATE(), 23)   -- 2026-04-23 (ISO date)

-- FORMAT (.NET) - flexible but slow:
FORMAT(GETDATE(), 'yyyy-MM-dd')          -- 2026-04-23
FORMAT(GETDATE(), 'dd-MMM-yyyy')         -- 23-Apr-2026
FORMAT(GETDATE(), 'hh:mm tt')            -- 02:30 PM
FORMAT case sensitivity (huge gotcha): MM = month, mm = minutes; HH = 24-hour, hh = 12-hour. 'yyyy-mm-dd hh:mm' gives you minutes-where-month-should-be and a 12-hour clock. Always 'yyyy-MM-dd HH:mm'. 
-- Safe conversions: return NULL instead of erroring  (2012+)
TRY_CAST('not a date' AS DATE)        -- NULL (no error)
TRY_CONVERT(DATE, '2026-13-40')         -- NULL

-- PARSE / TRY_PARSE: culture-aware string -> date (slow, CLR)
PARSE('23/04/2026' AS DATE USING 'en-GB')   -- 2026-04-23
TRY_PARSE('April 23, 2026' AS DATE USING 'en-US')
Force decimal division (common interview trap): CAST(COUNT(*) AS DECIMAL(10,2)) / total or 1.0 * COUNT(*) / total. Without it, 1 / 2 = 0 (integer division).

7. Time zones

AT TIME ZONE, SWITCHOFFSET, and TODATETIMEOFFSET - the trio the reference didn't cover but interviewers love.

-- AT TIME ZONE: attach or convert time zones  (2016+)
-- 1) Treat a naive datetime as being in a zone (attaches offset):
'2026-04-23 14:00' AT TIME ZONE 'Eastern Standard Time'
--   -> 2026-04-23 14:00:00 -04:00

-- 2) Convert one zone to another (chain two AT TIME ZONE):
SYSDATETIMEOFFSET() AT TIME ZONE 'UTC'
                      AT TIME ZONE 'India Standard Time'

-- Store UTC, display local:
SELECT OrderDate AT TIME ZONE 'UTC' AT TIME ZONE 'Pacific Standard Time'
FROM Orders;

-- SWITCHOFFSET: same instant, different offset (keeps the point in time)
SWITCHOFFSET(SYSDATETIMEOFFSET(), '+05:30')

-- TODATETIMEOFFSET: attach an offset to a naive datetime (does NOT convert)
TODATETIMEOFFSET('2026-04-23 14:00', '-05:00')
SWITCHOFFSET vs TODATETIMEOFFSET: SWITCHOFFSET keeps the same instant and recomputes the wall-clock time for the new offset. TODATETIMEOFFSET just labels a naive value with an offset (no conversion). Mixing them up silently shifts your times.

9. Master gotchas

GotchaWhat happens / how to avoid it
DATEDIFF counts boundary crossingsDec 31 -> Jan 1 = 1 YEAR even though 1 day apart. Don't use it to measure "full" periods without adjusting.
DATEDIFF argument order(part, start, end) = end - start. Swapping flips the sign.
DATEADD(MONTH,...) clampsDATEADD(MONTH, 1, '2026-01-31') = 2026-02-28, not 03-03. Great for month-end, surprising otherwise.
DAY() resets across monthsDAY returns day-of-month (1-31). Jan 31 -> Feb 1 is 31 then 1. Never use it for date arithmetic; use DATEADD/DATEDIFF.
FORMAT is slow (CLR)Avoid in WHERE/JOIN/large sets. Use CONVERT for performance; FORMAT for final display only.
FORMAT case: MM vs mm, HH vs hhMM=month, mm=minutes, HH=24hr, hh=12hr. Getting this wrong silently produces garbage output.
Functions on columns kill indexesWHERE YEAR(OrderDate)=2026 is non-SARGable (no index seek). Prefer a range: OrderDate >= '2026-01-01' AND OrderDate < '2027-01-01'.
BETWEEN on datetime misses the last dayBETWEEN '2026-01-01' AND '2026-01-31' excludes times after midnight on the 31st. Use < '2026-02-01' instead.
Ambiguous string literals'04/05/2026' depends on DATEFORMAT/language. Always use ISO '2026-04-05' or '20260405' for unambiguous, culture-safe literals.
DATETRUNC / DATE_BUCKET need 2022+On older servers use DATEADD(MONTH, DATEDIFF(MONTH, 0, d), 0) for month truncation.
CURRENT_DATE needs 2025+Use CAST(GETDATE() AS DATE) for date-only on older versions.
DATEDIFF INT overflowDATEDIFF(SECOND, veryOld, now) can overflow INT (~68 yrs). Use DATEDIFF_BIG.
WEEKDAY depends on SET DATEFIRSTWeek-day numbers shift with server/session settings. Use ISO_WEEK or DATENAME for stability.

10. Interview tips & decision tree

Quick-fire tips

  • No DATETRUNC before 2022 - use DATEADD(MONTH, DATEDIFF(MONTH, 0, d), 0).
  • No CURRENT_DATE before 2025 - use CAST(GETDATE() AS DATE).
  • DATEDIFF counts boundary crossings, not full intervals.
  • EOMONTH for month-end - avoids 28/29/30/31 handling.
  • DATENAME only for MONTH/WEEKDAY; else it's just a number-as-string.
  • CAST by default (ANSI); CONVERT for style codes; FORMAT for display only.
  • Keep predicates SARGable - avoid wrapping the column in a function.
  • Mention ANSI vs SQL Server portability - shows awareness.
FUNCTION DECISION TREE

Need current datetime?
  -> CURRENT_TIMESTAMP (ANSI) or GETDATE()
  -> UTC? GETUTCDATE() / SYSUTCDATETIME()

Need to extract a part?
  -> Need 'April'/'Thursday'? DATENAME()
  -> Need a number?           DATEPART() (or DAY/MONTH/YEAR)

Add/subtract time?  -> DATEADD(part, n, date)
Difference?         -> DATEDIFF(part, start, end)
  -> huge range?    -> DATEDIFF_BIG(...)

Group by time bucket?
  -> Fixed 1-unit?  DATETRUNC(part, date)     (2022+)
  -> Custom N-unit? DATE_BUCKET(part, N, date)(2022+)

Last day of month? -> EOMONTH(date)

Type conversion?
  -> No formatting? CAST (ANSI)
  -> Style code?    CONVERT
  -> Custom pattern?FORMAT (slow, display only)
  -> Might fail?    TRY_CAST / TRY_CONVERT

Time zones?
  -> Convert zones? AT TIME ZONE
  -> Same instant?  SWITCHOFFSET
  -> Label offset?  TODATETIMEOFFSET
